01 / Adapter

El Patrón
Adapter

Permite que objetos con interfaces incompatibles colaboren entre sí. Convierte la interfaz de una clase en otra que el cliente espera.

  • Envuelve un objeto para ocultar su interfaz
  • Reutiliza código existente sin modificarlo
  • También conocido como Wrapper
Patrón Estructural — GoF (1994)

01 / Adapter — Implementación Java

// Interfaz esperada por el cliente interface Reproductor { void play(String archivo); } // Clase existente — interfaz incompatible class ReproductorLegado { public void reproducirMP4(String ruta) { System.out.println("Play: " + ruta); } } // Adaptador: envuelve lo incompatible, expone lo esperado class AdaptadorMP4 implements Reproductor { private final ReproductorLegado adaptado; AdaptadorMP4(ReproductorLegado r) { this.adaptado = r; } @Override public void play(String archivo) { adaptado.reproducirMP4(archivo); } }

02 / Builder

El Patrón
Builder

Separa la construcción de un objeto complejo de su representación final. Permite crear diferentes representaciones con el mismo proceso.

  • Construye el objeto paso a paso con interfaz fluida
  • El Director orquesta la construcción
  • Elimina constructores con demasiados parámetros
Patrón Creacional — GoF (1994)

02 / Builder — Implementación Java

class Reporte { String titulo, cuerpo; static class Constructor { private final Reporte r = new Reporte(); Constructor titulo(String t) { r.titulo = t; return this; } Constructor cuerpo(String c) { r.cuerpo = c; return this; } Reporte build() { if (r.titulo == null) throw new IllegalStateException("Falta título"); return r; } } } // Uso — interfaz fluida Reporte informe = new Reporte.Constructor().titulo("Q3").cuerpo("Datos").build();

03 / Iterator

El Patrón
Iterator

Proporciona una forma de acceder secuencialmente a los elementos de una colección sin exponer su representación interna.

  • Abstrae la estructura interna de la colección
  • Mismo código de traversal para distintas colecciones
  • Base del patrón for-each moderno
Patrón de Comportamiento — GoF (1994)

03 / Iterator — Implementación Java

// Contrato del iterador interface Iterador<T> { boolean hasNext(); T next(); } // Colección que expone su propio iterador class Catalogo { private final String[] items; Catalogo(String[] items) { this.items = items; } public Iterador<String> iterator() { return new Iterador<String>() { private int pos = 0; public boolean hasNext() { return pos < items.length; } public String next() { return items[pos++]; } }; } }

Análisis de Trade-offs

Adapter

+ Sin modificar código base

+ Reutilización de legado

– Aumenta complejidad general

Builder

+ Construcción fluida y legible

+ Previene inconsistencias

– Requiere múltiples clases

Iterator

+ Traversal uniforme

+ Abstrae la estructura interna

– Overhead vs. for-each nativo

¿Cuándo usar cada patrón?

Adapter

  • Código legado inmodificable
  • Librerías con API incompatible

Builder

  • Constructores gigantes
  • Pasos de creación en orden estricto

Iterator

  • Estructura interna muy compleja
  • Múltiples formas de recorrer datos

Conclusiones

  • Adapter: Integra sistemas existentes sin riesgo.
  • Builder: Domina la complejidad constructiva.
  • Iterator: Unifica el acceso a los datos.

Los patrones GoF proporcionan un vocabulario arquitectónico compartido que facilita la comunicación en ingeniería de software.
